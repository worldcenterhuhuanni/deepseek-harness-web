# Agent Note：网页桥把页面作为通道单独记账，与对话基线分开

Status: implemented

[English](2026-08-19-deepseek-web-blocked-page-channel.md) | 中文

## Problem

一次 `deepseek-web` 运行停在半路，之后每一轮都以同一句话失败：

```
turn/end reason=error  无法发送消息：点击与回车都没有让输入框清空，页面可能已改版。 TRANSPORT
```

turn 9 前十一步全部正常（`read`、`edit`、`bash` 都执行了），死在第十二步。真正的原因写在页面上：八张 `context.md` 卡片各约 244KB 堆在同一个输入框里，下面是站点自己的提示——`请删除异常文件再发送`。其中一张显示 `服务器繁忙`：那是一次撞上站点故障的上传。从它出现那一刻起，站点就一直禁用发送键。

日志里有九次发送尝试（三轮 × 一次初始加两次重试）。第一次在 324ms 内以 `EMPTY_RESPONSE` 失败，快到不可能挂上任何东西；其余八次都走到了 `attach()`，各留下一张卡片。数目与页面完全对得上。

三个缺陷叠在一起：

- **词表不认识这句提示。** `FAIL_HINT` 收的是 `解析失败|未能发送|发送失败`，没有这句拒绝，于是 `attach()` 报「附件已就绪」。
- **`waitSendable()` 的返回值被丢掉了。** 永久禁用的发送键照点，三种提交方式随后全部失败，而错误写的是 `页面可能已改版`——这句话里没有任何来自页面的信息。
- **`TRANSPORT` 把持久故障和偶发故障混成一类。** 它在 `retryableCodes` 里，于是 `dsh-llm-retry` 忠实地重发本轮——发到同一个已死的页面上，每次再挂一个 244KB 附件。

## 决定

失败记账带两个相互独立的维度。

`conversation` 回答的一直是「内容基线还能不能用」，判据是 `submitted` 里程碑。缺的是「承载它的页面还能不能用」。两者确实独立：站点在输入区留下一张坏掉的附件卡片并禁用发送，而对话内容一个字没变。`channelBlocked` 记录后者，`resumeBlocker` 优先于内容判据消费它，于是下一轮开一条新对话并带全量历史——走的都是新开对话本来就有的路径。

桥接层的 `page-blocked` 映射到新错误码 `PAGE_BLOCKED`，由 `providerRetryPolicy()` 追加进配置里的 `retryableCodes`，与 `UNPARSABLE_TOOL_CALL` 用的是同一套机制。所以恢复发生在本轮之内：拒绝发送 → 可重试失败 → 重试时发现通道已被标记不可用 → 换新对话 → 任务继续。

判定与消息现在都来自页面。`sendFailureFrom()` 是 `PageSnapshot` 的纯函数：命中拒绝词表就报站点原话并归 `page-blocked`，没命中就原样引用输入区文本（`hint`）。等发送键那一步同样按这个方式失败，而不是对着一个禁用的控件点三次。

这条路径上的每个词表与每个超时都成了 `Config` 字段，默认值只有一处 home（`DEFAULT_PAGE_HINTS`、`DEFAULT_*_TIMEOUT_MS`）。站点改一句文案就足以让写死的词表失灵；现在改配置下一次读取即生效。

## Alternatives considered

**改 loop。** 可以给 `agent/request-error` 加一种动作，语义是「先复位 provider，再重发」。它输在契约本来不需要：那个承诺只是判断一个失败值不值得重发，请求内容不变，provider 用哪条通道满足它属于 provider 的实现细节。缺口在 provider 的状态机上，改 loop 就是改错层——而仓库的规则是加插件、不改 loop。

**清理残留的附件卡片。** 删掉残留就能让同一个页面继续用下去。它输在脆弱：站点只在 hover 时才显出删除控件，那是能选到的最脆的选择器，而换一条新对话本来就让残留不再相关。现在没有任何地方清理附件，也不需要——发送成功时站点自己会清空，只有失败才留下残留。

**词表继续写在注入脚本里，只补上缺的那句。** 一行就能修掉这一例。它输在这个失效模式会重复：词表内容是站点 UI 文案，下一次改文案又会失灵，而那只能靠插件发版解决。做成 Config 字段就把纠正的手段交到了用户手里。

## Consequences

恢复现在发生在本轮之内，一次拒绝的代价是一次重试，而不是任务终止。代价是恢复后的那一轮以附件重发全量历史而不是增量——这没法避免，新开的对话不记得前面的轮次。

`page-blocked` 的能力上限就是它的词表。站点换个说法拒绝时仍按 `TRANSPORT` 失败，但错误消息现在原样引用输入区文本，缺哪一句因此看得见；补进去是改配置。这一条作为已知限制记在包 README 里。

各部分都由单元测试钉住：通道维度走既有的 `continuesAfter` 宿主，自证失败走 `sendFailureFrom`，还有空词表一例（否则 `new RegExp('')` 会匹配一切）。没有 keyless snapshot 覆盖其中任何一项——这条路径需要真实浏览器与登录态，回放宿主给不了。同样的原因，这个包整体豁免 per-file 100% 覆盖率门禁：它的驱动层（`cdp.ts`、`launch.ts`、`session.ts`）只在真实 Chrome 上执行。

注入脚本另外在真实站点上验证过，因为 jsdom 通过不等于真实页面通过：从构建产物 `lib/` 载入 `PAGE_AGENT`，干净页面不误判任何一项，把站点那句拒绝插进真实输入区能被认出，移除后判定归零。正是这次运行发现 `hitLine` 会把模式切换菜单的文字卷进消息里——真实 `innerText` 带换行，命中所在的那一行才是站点写的那句话。

# Agent Note：网页桥只解析最终快照，并容忍页面实际产出的每种调用写法

Status: implemented

[English](2026-08-18-deepseek-web-snapshot-parsing.md) | 中文

## 问题

走 `deepseek-web` 路由的一次 `dsh --profile` 运行停在半路：模型要调工具，回合却结束了，什么也没执行。turn 1 step 3 的会话日志里，那条 assistant 消息的正文把同一段话重复了四遍，每遍略有不同，`tool-call` block 一个都没有，`turn/end` 记的是 `{ kind: 'completed' }`。

`agent-loop` 的行为是对的。`ReactLoopAgent.step` 只要看到 assistant 消息带工具调用就进入下一 step，一个都没有才结束回合。provider 交上来的就是零个，循环只能把这条回复当成最终答案。

丢失发生在 `WebSession.consume`。页面报的是**全量正文快照**，而桥接层把它当成了增量：

```
const delta = fresh.startsWith(emitted) ? fresh.slice(emitted.length) : fresh
```

DeepSeek 网页会回头改写已渲染的文本——markdown 重排、转义修正。抓到的日志里就有一处原样可见：两次快照之间，`-name ".ts\"` 变成了 `-name "*.ts"`。改写破坏了 `startsWith` 的前缀关系，兜底分支于是把**整份快照**当作新增输出发了出去。`ToolCallSplitter` 只追加不回退，四次改写就拼出了四份回复。

拼接摧毁了标记配对：某一份里打开的 `<tool_call>`，后面紧跟的是下一份的正文，它的 `</tool_call>` 永远不会到达，`flush()` 只好把整段当可见文本交出去。还有第二个缺陷叠加在上面——切分器用 `indexOf('<tool_call>')` 找开标签，而模型写的是 `<tool_call name="read">`，这种比较看不见它。

## 决定

桥接层报快照，适配器在生成结束后只解析一次。

`BridgeEvent` 的 `text` 现在携带完整正文而非增量；`DsWebAdapter.stream` 只留最新的一份，在流结束时对它跑一次 `splitReply`。增量解析是在跟一个会自我修订的数据源较劲：页面停止改写之前，标记的两半都不稳定，再多缓冲也不能让半截回复安全切分。

代价是正文不再逐字流式。这条路由的用途是给 dsh 供 token，不是渲染打字动画；而一个默默吞掉全部工具调用的回合，比一次性出现的回合糟糕得多。

在完整回复上解析也让格式容错变得廉价，`splitReply` 兜住模型跑格式的三种写法：

- **开标签带属性。** `/<tool_call\b[^>]*>/` 接受 `<tool_call name="read">`。
- **调用未闭合。** 调用体延伸到文末，而不是让整段退化成正文。
- **完全没写标记。** 裸的顶层 `{"name":…,"arguments":…}` 会被认领为调用——但仅限它的名字出现在本轮工具表里，普通回复里的 JSON 不会被误判。`jsonObjectEnd` 只在字符串字面量之外数括号，参数值里的 `{` 不会让扫描失衡。

## 协议只是建议，重量落在解析器上

修掉拼接远不够——之后三次实跑各自栽在不同的格式问题上，合起来划定了这条通路能保证什么、不能保证什么。

**站点自己的系统提示词压过我们的。** 整个请求走附件时，某次运行回的是 `[调用 glob] {"pattern": …}`：它叫出的工具名只可能来自附件里的目录，却自创了调用语法。附件被当作文档来读，只有输入框里的文字被当作指令。所以 `TOOL_CALL_PROTOCOL` 现在每轮都随输入框发送，`renderBlocks` 也按同一种代码块形式回放历史调用——模型会模仿它见过的写法。一次 CDP 探测确认输入框逐字保留了这段文字：模型收到了协议，仍然偏离。位置只提高命中率，不能把格式变成保证。

**渲染后的代码块丢掉了围栏。** 等模型真的照做时，回复长这样：`<tool_call>\n\njson\n复制\n下载\n{…}`——`innerText` 留下了语言标签和代码块自己的「复制/下载」按钮文字，唯独没有反引号。`parseToolCall` 因此改为从调用体里取**第一个平衡的 JSON 对象**，而不是整段 parse；这跳过了那些残留，也顺带取代了它原来剥围栏的做法。

所以 `splitReply` 的宽容不是防御式编程，而是这条通路的运行条件。目前认四种形式：协议规定的代码块调用、带属性或缺闭标签的标记、裸 `{"name":…,"arguments":…}` 包装、以及叙述式 `[调用 name] {参数}`。后两种以本轮工具名为闸门。

把 JSON 放进代码块也消除了最初那份报告背后的转义损坏：围栏之外，页面会把 `\"` 渲染成 `"`，任何带引号参数的调用都会变成坏 JSON。

## 考虑过的其他方案

- **改写时发公共前缀。** 三行改动，确实能止住拼接。否决是因为它修不好回复：已经发出的文本收不回来，改写前那个 `.ts\"` 转义仍留在流里，它那条工具调用照样解析失败。这是治了重复、留下了损坏。
- **强迫模型遵守协议。** 试过，也测过：协议逐字到达了输入框，模型照旧用自己的语法。跟一个我们控制不了的系统提示词较劲不是修复；识别模型实际输出的形式才是。
- **流式发稳定前缀，末尾再解析尾部。** 保住了打字动画，但需要一条规则来判断落后快照头部多远的文本可以安全发出，而这条规则得知道标记可能从哪里开始——包括无标记的那种写法，它根本没有开标签可找。这些复杂度换来的，是一条本来就每 120ms 轮询一次 DOM 的路由上的动画。

## 影响

`deepseek-web` 上要调工具的回合现在能真的调起来：循环拿到了此前被吞掉的 `tool-call` block，从而进入下一 step。回复在生成结束时整段到达，不再逐字增长；会话日志里重复的回复文本也消失了——那从来不是模型的输出，只是桥接层自己拼出来的。

`ToolCallSplitter` 被删除，随它一起消失的还有那套扣住尾部字节的缓冲逻辑，它存在的唯一理由就是让标记匹配能跨 chunk 边界安全工作。包的公开导出里由 `splitReply(text, knownTools)` 接替。

裸 JSON 兜底以本轮工具名为闸门，所以一条讨论「某个未提供工具的 `{"name":…,"arguments":…}` 载荷」的回复仍是可见文本。若讨论的恰是本轮提供的工具，它会被认领为调用；这里没有任何手段区分这两种情况，闸门就是把这个缺口限制到最小的东西。

## 测试

`tests/parse.spec.ts` 覆盖切分器的格式容错，包括那份解析出零个调用的真实回复。`tests/snapshot-stream.spec.ts` 用连续的改写快照驱动 `DsWebAdapter`，断言只有一个 tool-call block、正文不重复、finish 原因为 `tool-calls`。
